# US-03-05 — Enregistrement du dossier en brouillon et complétion progressive

## Objectif

Permettre au client d’enregistrer son dossier comme **brouillon** et de le **compléter sur plusieurs sessions**, tout en étant **relancé** lorsqu’un brouillon reste **sans soumission** trop longtemps.

## Critères DoD

| Critère | Statut |
| -------- | ------ |
| Les informations saisies sont sauvegardées automatiquement | Déjà en place (hors périmètre de cette livraison) |
| Le brouillon est accessible depuis l’espace client | Déjà en place (liste `mes-dossiers`) |
| **Un brouillon non soumis après 30 jours déclenche une notification de rappel** | Implémenté (voir ci-dessous) |

Pour le rappel : référence métier **`created_at`** + **30 jours calendaires** (fuseau : UTC en exécution batch), avec **une seule notification par dossier** grâce à la colonne `draft_reminder_sent_at`.

## Implémentation technique

### Backend

1. **Modèle** `app/models/dossier.py`  
   - Colonne **`draft_reminder_sent_at`** (`DateTime(timezone=True)`, nullable) : horodatage du premier (et seul) envoi du rappel pour ce dossier.

2. **Migration Alembic**  
   - `backend/alembic/versions/004_us_03_05_draft_reminder.py`

3. **Configuration** `app/core/config.py`  
   - **`DRAFT_REMINDER_AFTER_DAYS`** (défaut : `30`) pour ajuster le délai sans modifier le code.

4. **Email** `app/services/emailing.py`  
   - **`send_draft_reminder_email`** (+ gabarit HTML aligné sur les autres mails transactionnels)  
   - Lien vers **`{FRONTEND_BASE_URL}/mes-dossiers`**.

5. **Traitement métier** `app/services/draft_reminders.py`  
   - **`process_stale_draft_reminders(db, *, now, stale_after_days=None)`** : sélection des dossiers `brouillon`, sans `submitted_at`, sans rappel déjà envoyé, `created_at ≤ now − N jours`, clients non supprimés (`deleted_at IS NULL`), envoi puis `commit` par dossier avec mise à jour de **`draft_reminder_sent_at`**.

6. **Job CLI** `app/jobs/remind_stale_draft_dossiers.py`  
   - Commande : **`python -m app.jobs.remind_stale_draft_dossiers`**  
   - À planifier **quotidiennement** (CronJob Kubernetes, systemd timer, plateforme d’orchestration, etc.) avec les **mêmes secrets / variables** que l’API (base, `SECRET_KEY`, `FRONTEND_BASE_URL`, `RESEND_*`).

### Variables d’environnement

Les variables **`RESEND_API_KEY`** et **`RESEND_FROM_EMAIL`** sont réutilisées comme pour les autres emails ; sans clé Resend (ou en cas d’échec d’appel API), **aucun** horodatage **`draft_reminder_sent_at`** n’est écrit : le job pourra **réessayer** au prochain passage.

### Frontend

Aucun changement requis : la notification est **email** ; le parcours **mes dossiers** existant couvre l’accès aux brouillons.

## Tests ajoutés

### Backend (`tests/unit/test_draft_reminders.py`)

- Pas de rappel si le brouillon est **récent** (< 30 jours artificiels dans le test).
- **Envoi simulé** pour un brouillon **anciens**, vérification des paramètres (`email`, référence dossier, URL `…/mes-dossiers`) et persistance de **`draft_reminder_sent_at`** (compatibilité horodatage SQLite / PostgreSQL dans l’assertion).
- Pas de **deuxième** envoi si `draft_reminder_sent_at` est déjà défini.
- Ignorer les dossiers dont le statut **n’est plus `brouillon`**.
- `send_draft_reminder_email` avec **Resend non configuré** : pas d’exception, retour **`False`**.
- Si l’envoi retourne **`False`**, **`draft_reminder_sent_at`** reste **`NULL`**.
